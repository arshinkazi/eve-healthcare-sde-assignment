# EVE Healthcare - SDE Intern Backend Assignment

A small FastAPI + PostgreSQL backend for diagnostic-test bookings and simulated payments.

Built to directly address the assignment requirements: JWT authentication, diagnostic centres/tests, bookings, mock payments, an idempotent payment webhook, edge-case handling, tests, Docker, pagination, structured logging, and OpenAPI documentation.

## 1. Tech stack

- Python 3.12
- FastAPI
- SQLAlchemy 2
- PostgreSQL 16
- JWT authentication with PyJWT
- Argon2 password hashing via `pwdlib`
- Pytest + FastAPI TestClient
- Docker / docker-compose
- OpenAPI/Swagger generated by FastAPI

The assignment allows FastAPI and prefers PostgreSQL.

## 2. Architecture

```text
Client
  |
  v
FastAPI routes
  |
  +--> JWT auth / authorization
  |
  +--> Booking service ----> SQLAlchemy ORM ----> PostgreSQL
  |
  +--> Payment service ----> Payment + Booking transaction
  |
  +--> Webhook ------------> idempotency key (provider_event_id)
```

### Main entities

- `users`: authenticated patients
- `diagnostic_centres`: centre name/location
- `diagnostic_tests`: reusable test definitions
- `centre_tests`: many-to-many centre/test relationship with centre-specific price
- `bookings`: patient appointment and price snapshot
- `payments`: one payment per booking and provider event id

A booking stores the price at booking time so later catalogue price changes cannot alter an existing booking.

## 3. Booking lifecycle

```text
                +----------------+
                |    PENDING     |
                +----------------+
                  /            \
        SUCCESS  /              \  FAILED
                v                v
        +-------------+    +-----------+
        |  CONFIRMED  |    |  FAILED   |
        +-------------+    +-----------+
               ^
               |
        cancellation only
        while still pending
               |
        +--------------+
        |  CANCELLED   |
        +--------------+
```

Payment success confirms a pending booking. Payment failure marks it failed. Cancelled bookings cannot subsequently receive a payment.

## 4. Why the webhook is idempotent

The provider sends a stable `event_id`.

`payments.provider_event_id` has a database-level UNIQUE constraint. Before creating a payment, the webhook looks up the event:

1. If the event was already processed with the same booking/status, return the existing payment.
2. If the same event ID is reused with different data, return `409 Conflict`.
3. Otherwise create one payment and update the booking.
4. The database constraint provides a second line of defence against duplicate event processing.

This directly addresses the assignment requirement that repeated webhook events must not create duplicate payments/bookings or corrupt state.

## 6. Run locally with Docker

```bash
git clone  https://github.com/arshinkazi/eve-healthcare-sde-assignment.git
cd eve-sde-intern-assignment

cp .env.example .env
docker compose up --build
```

API:
`http://localhost:8000`

Swagger:
`http://localhost:8000/docs`

The database is automatically initialized on application startup.

## 7. Run without Docker

Create a virtual environment and install dependencies:

```bash
python -m venv .venv

# macOS/Linux
source .venv/bin/activate

# Windows
.venv\Scripts\activate

pip install -r requirements.txt
```

For the simplest local development/test setup, SQLite is supported through the default configuration. 
For the assignment deployment, PostgreSQL is the intended database.

Then:

```bash
uvicorn app.main:app --reload
```

## 8. Example API flow

### Create a user

```bash
curl -X POST http://localhost:8000/auth/signup \
  -H "Content-Type: application/json" \
  -d '{
    "email": "arshin@example.com",
    "password": "password123",
    "full_name": "Arshin"
  }'
```

### Login

```bash
curl -X POST http://localhost:8000/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "email": "arshin@example.com",
    "password": "password123",
    "full_name": "Arshin"
  }'
```

Copy the returned `access_token`.

### Create a centre

```bash
curl -X POST http://localhost:8000/centres \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name":"EVE Diagnostics","location":"Jaipur"}'
```

### Create a test

```bash
curl -X POST http://localhost:8000/tests \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name":"CBC","description":"Complete Blood Count"}'
```

### Attach a test to a centre with a price

```bash
curl -X POST http://localhost:8000/centres/1/tests \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"test_id":1,"price":"499.00"}'
```

### Book

`appointment_at` must include a timezone and must be in the future.

```bash
curl -X POST http://localhost:8000/bookings \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "centre_id": 1,
    "test_id": 1,
    "appointment_at": "2026-10-10T10:00:00+05:30"
  }'
```

### Simulate successful payment

```bash
curl -X POST http://localhost:8000/payments/ \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"booking_id":1,"outcome":"SUCCESS"}'
```

### Simulate a provider webhook

```bash
curl -X POST http://localhost:8000/payments/webhook \
  -H "Content-Type: application/json" \
  -d '{
    "event_id":"evt_001",
    "booking_id":1,
    "status":"SUCCESS"
  }'
```

Send the exact same webhook again: it returns the existing payment instead of creating another one.

## 10. Important assumptions

1. This is intentionally a single-service backend; no real payment provider is integrated.
2. A user is treated as the patient.
3. A centre/test pair has one current price.
4. The booking snapshots the current price.
5. The assignment does not specify slot capacity, so this implementation prevents the same user from creating an identical booking but does not impose an arbitrary one-booking-per-centre-time capacity across all users.
6. Catalogue-management endpoints are authenticated, but there is no separate admin role because the assignment does not define roles.
7. Webhooks are trusted as simulated provider callbacks. A production implementation would also validate a provider signature.
8. `Base.metadata.create_all()` keeps the assignment easy to run. Production deployment would use Alembic migrations.

## 11. What I would improve with more time

- Admin role/permissions for catalogue management.
- Provider webhook signature verification.
- Redis-backed rate limiting and caching.
- Celery/background jobs for asynchronous payment processing.
- Appointment-slot availability/capacity model.
- Database-level concurrency strategy for high-volume booking/payment races.
- Metrics/tracing and centralized structured logs.
- CI pipeline with linting, type checking, tests, and coverage.
- Refresh-token rotation and token revocation.
- PostgreSQL integration tests in CI.

## 12. Assignment alignment

The brief emphasizes engineering thinking over raw feature count and specifically values a smaller, well-designed, tested solution. The implementation therefore prioritizes clear boundaries, database constraints, authorization, transactional state changes, and focused tests rather than adding unnecessary infrastructure.
